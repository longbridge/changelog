# Rewriting Release Notes for the public

> Paths are relative to the repo root: source data lives in `releases/`, code in `app/`. Run `bun run` commands inside `app/`.

Turn the internal release notes fetched into this repo into a changelog that users can understand and that is safe to publish.

## Where this sits in the data flow

```
releases/<product>/<tag>.<locale>.md ← source text fetched by bun run fetch (frontmatter has fetchedAt), read-only
app/src/content/releases/zh-CN/...mdx    ← first draft generated by bun run transform; this skill rewrites it
app/src/content/releases/zh-HK|en/...    ← translated from the finalized zh-CN
app/src/content/majors/<locale>/...mdx   ← major-version summaries; transform only creates empty shells, this skill writes the content
```

**Do not modify the fetched source text** (`releases/<product>/<tag>.<locale>.md`); a re-fetch overwrites it. A `<version>.md` without frontmatter in the same directory is a product manager's handwritten draft — that goes through `release-page-compose`.

This is a public repo: rewritten copy must not contain internal system names, internal links, people's names, or features not yet public.

## Two-level structure

The site is organized by **major version**: the first two segments of the version number are the major (`0.20.1` → `0.20`; date versions `2026.09.11` → `2026.09`).

- **The list page shows only major versions**: readers see the major's title and summary, which come from `app/src/content/majors/`
- **Inside a major's page, sections are per minor version**: each minor's title and body come from `app/src/content/releases/`, and the sidebar jumps between minors

So for a version to appear on the site, both are required: the minor is `published`, **and** the major summary it belongs to is `published` in all three locales.
`bun run check:assets` flags anything that's only half done.

## Three references

The rules live in `references/`, in the order you'll need them:

| File | When to read |
| --- | --- |
| [`classification.md`](references/classification.md) | Before writing. Picking which items from the source are worth writing — including checking "Reverted", deployment-unit audience, and the six screening questions |

## Steps

1. Confirm scope: the product / version the user named, or every entry with `status: draft`.
2. **First confirm the source is complete**: the `github` source only captures tags that have a Release object; versions without a Release
   don't show up at all. Count them, and fill gaps from the upstream repo's git log — especially when compiling a whole month. See section 0 of `classification.md`.
3. Read the draft MDX, and read the source `releases/<product>/<tag>.<locale>.md` as the factual basis.
   **Don't skip the source's three tables (Reverted / Affected deployment units / Shared package changes)**; they decide which items
   shouldn't be candidates at all. If the source mentions a product concept you haven't seen before, search git for where it came from — a lone fix
   may be the tail of an entire feature.
4. Pick the items to write per `classification.md`, rewrite the body per the rules below, and fill in `summary` and `highlights`.
   **A minor version covers only 1–3 things; a major summary only 3–4**; fold the rest in or leave it out.
5. Change `status` from `draft` to `published`.
6. Translate to the other locales: finalize zh-CN first, then produce zh-HK and en; keep the number and order of `highlights` identical across all three.
7. Write or update the **major-version summary** these versions belong to (see next section).
8. When done, run `bun run check:assets` and `bun run build` to confirm they pass.

## Major-version summaries

`app/src/content/majors/<locale>/<product>/<major>.mdx`. `transform` only creates an empty shell:

```yaml
title: Longbridge Pro 0.20   # placeholder, must be changed
summary: ''
highlights: []
status: draft
```

What you write is **what this whole major version brings users**, not the minor versions' notes stitched together:

- `title`: one sentence, same rules as a minor's title
- `summary`: one sentence, within 40 characters (Chinese), covering the one or two things most worth saying about this major
- `highlights`: 2–4 short phrases, the highlights of the whole major, not of any one minor
- The body can stay empty — the details are in the minor sections below; repeating them only makes the page longer
- Only change `status` to `published` once all three locales are done

When a new minor joins an already-published major, re-check whether the summary is still accurate: if it adds a feature worth mentioning, add it to `highlights`;
if it's only fixes, leave it alone.

## Rewriting rules

**Perspective**: write the change the user can perceive, not the implementation.

- ✗ `桌面端 view 切换支持 widget 不销毁` (desktop view switching keeps widgets alive) → ✓ `切换页面后返回，行情与自选状态保持不变` (switch away and back, and quotes and watchlist state stay as they were)
- ✗ `体验优化 - Dropdown 控件优化` (UX optimization – Dropdown control optimization) → ✓ `下拉菜单操作更顺滑` (dropdown menus feel smoother)
- ✗ `多租户配置迁移到配置平台` (multi-tenant config migrated to the config platform) → irrelevant to users, delete it

**Must delete**: internal system/service names (config platform, gateway, "such-and-such service"), code symbols (component names, API names, field names), people's names and employee IDs, internal links, MR/issue numbers, pure refactors and ops changes, features not yet public.

**Merge duplicates**: the source often splits one feature across several lines (e.g. 「资产交易支持美股做空」 / 「资产支持美股做空」, both about US short selling); merge them into one complete statement.

**Grouping**: the body uses H2 headings `## 新增功能` (New) / `## 体验优化` (Improved) / `## 问题修复` (Fixed), one list item per entry within each group. Delete any group that has no content; don't leave empty headings.

**Not every tag deserves its own section**: fetching follows release tags, but readers care about features. If a tag only has
one or two pure fixes and can't support a title, mark it `status: skipped` and fold its items into the adjacent version's `## 问题修复` (Fixed).
The test is "is this section worth a screen of the reader's attention", not "was this tag shipped".

Conversely, when one feature ships across several tags (page first, then filters, then fixes), write it as one complete
statement under the version where the feature came together; don't write it once per tag.

A `skipped` version still keeps its file and frontmatter — it records that the release really happened, it just doesn't get its own section.
`check:assets` only checks `published` entries, so a `skipped` body can be emptied; but **mark all three locales
`skipped` together** — marking only one locale makes the other two "published but missing a locale".

**Length**: one sentence per item, 20–40 characters (Chinese); `summary` is one sentence summarizing the release (max 60 characters); `highlights` are the 2–5 things most worth saying, short phrases shown on the list page (max 20 characters), no trailing period.

**When the source is empty**: the draft contains a `{/* 原始 Release 说明为空 */}` ("original Release notes empty") comment. Do not invent features; ask the user instead, or mark the entry `status: skipped` (not shown publicly).

## Filling in entries awaiting translation

The fetch and transform stages **do no machine translation**; translation is this skill's job — machines get financial terms and Hong Kong usage wrong.

When a locale is missing, the scripts behave in one of two ways, depending on whether the source is public-facing copy:

| Source | When a locale is missing | Visible in `i18n:todo`? |
| --- | --- | --- |
| `repo-docs` / `appstore` / `release-api` | Generates a placeholder from the closest locale, marked `translation.status: pending` | Yes |
| `github` | **Generates nothing**; only the source-locale file exists | No |

So for internal-voice sources (`github` Releases), after rewriting **you must create the other two locale files yourself**:
copy the source locale's frontmatter, translate the body and `title` / `summary` / `highlights`,
and flip all three to `published` together. Forgetting gives no warning, but the site's language switcher falls back to the product page.

```bash
bun run i18n:todo            # list entries awaiting translation, with translation and source paths
bun run i18n:todo --locale en
```

Handle each one:

1. Open the `原文` (source) and `译文` (translation) files; the translation still holds placeholder content in the source language
2. Translate the body, `title`, `summary`, and `highlights` into the target locale following the conventions below
3. **Structure must line up**: number and position of media blocks, number of list items, and group headings must correspond one-to-one; readers switching locales shouldn't find more or less content
4. Update frontmatter: set `translation.status` to `done`; once verified, set `status` to `published`
5. Run `bun run build` to confirm it passes

The fields `product` `version` `tag` `releasedAt` `platforms` `source` must be identical across locales — they describe the same release.

## Locale conventions

| Locale | Requirements |
| --- | --- |
| `zh-CN` | Simplified Chinese, mainland usage: 「登录」「信息」「网络」 |
| `zh-HK` | Traditional Chinese, Hong Kong usage: 「登入」「資訊」「網絡」. Do not just convert Simplified to Traditional character by character |
| `en` | Concise imperative/declarative sentences, capitalized first word, no trailing period. Terminology follows the English version of the Longbridge website |

Keep financial terms consistent across the three locales: 港股 / 港股 / HK stocks, 美股 / 美股 / US stocks, 做空 / 沽空 / Short selling, 自选 / 自選 / Watchlist, 持仓 / 持倉 / Positions.

## Frontmatter conventions

Edit only these fields; the rest (`product` `version` `tag` `releasedAt` `source`) are maintained by scripts — don't touch them:

```yaml
title: What changed in this release — not just the version number
summary: One-sentence summary, used on the list page and as the SEO description
highlights: [highlight phrase, highlight phrase]
status: published   # draft = unfinished / published = publicly visible / skipped = not shown
```

`title` is the only thing readers scan on the list page — the site adds the version number and date next to it, so the title should say "what this release
brings users", in product language users understand, reading like a sentence rather than a list of nouns:

- ✗ `Longbridge Pro 0.20.0` (script placeholder; only says which version)
- ✗ `LongbridgeAI、交易、期权` (module names side by side — "LongbridgeAI, trading, options" — not natural language)
- ✓ `LongbridgeAI 正式上线` (LongbridgeAI is officially live)
- ✓ `图表里直接下单改单` (place and amend orders right from the chart)
- ✓ `修复交易密码保护下的账户设置` (fixed account settings under trading-password protection — for a fix-only release, say what was fixed)

How to write it: one sentence, at most 16 characters (Chinese; 60 characters in English), no trailing period, no information-free words like
「优化」 (optimize) or 「体验提升」 (better experience). If a release touches several areas, pick the one or two most worth saying and leave the rest to `summary`.

The three locales correspond one-to-one, each in its own local phrasing: `图表里直接下单改单` / `圖表內直接落單改單` /
`Trade directly from the chart`.

**If the source has wording, use it; don't coin terms.** `title` / `summary` / `highlights` are fields the source doesn't have and we must add,
which makes them the most likely to come out sounding like AI:

- First take feature names and original phrasing from **that locale's own source text** (bold labels, the first few words of an item); each locale takes from its own,
  don't translate the Chinese into English yourself — if upstream en says `Dream Memory`, write `Dream Memory`
- When the source has no ready-made wording, describe it plainly following that market's changelog conventions: for mainland / Hong Kong use the in-product UI names;
  for English follow mainstream US product release notes (noun phrases like `New models and in-chat rewards`),
  no slogans
- No self-invented rhetoric or concepts: ✗ `越用越懂你` ("knows you better the more you use it") ✗ `Traceable financial data` ✗ `AI writes collaborative documents`
  — the source didn't say it, and readers wouldn't say it either
- This applies especially to curated sources (`repo-docs` / `appstore` / `release-api`): the body was written by product, so
  the fields you add should read as if written by the same person

## MDX capabilities

The body is MDX, and the site injects a set of components — **just write the tags, no import needed**:

```mdx
<Callout type="warning">本次升级后需要重新登录。</Callout>
```

`<Callout>` types are `info` (default), `warning`, and `success`.

Images, video, before/after comparisons, step-by-step walkthroughs, and interactive demos are rich-media enhancements handled by the `release-notes-media` skill —
it defines the asset spec and the restraint principles. Do that step after the copy is final; don't insert nonexistent asset paths during rewriting.
