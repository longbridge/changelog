# 文案口径

写给用户看的更新日志。三条硬规则：**不说黑话、不说废话、不写长句。**

违反其中任何一条，读者要么看不懂，要么看完不知道发生了什么。

## 一、不说黑话

黑话有两种，都要删。

**工程黑话**——实现细节泄漏出来的词。用户没有这些概念：

> 骨架　渲染　重绘　重排　表单　下拉　抽屉　弹层　吸顶　浮层　原生滚动　虚拟滚动
> 前缀　样式　脚本　字段　接口　缓存　埋点　直出　拆包　收敛　组件　容器　兜底　降级

**公司黑话**——内部开会说的词。出现在对外文案里只会显得空洞：

> 赋能　抓手　闭环　心智　链路　沉淀　对齐　打通　拉通　颗粒度　全链路　一站式　生态

改法不是换个同义词，而是**回到用户在屏幕上看到了什么**：

| ✗ 黑话 | ✓ 用户看到的 |
| --- | --- |
| 加载时的骨架补齐了形态 | 页面加载时不会再跳一下 |
| 改成滚多少渲染多少 | 长列表往下滚不卡了 |
| 修复 AI 抽屉挤到顶栏 | 打开 AI 问答不会再把顶部菜单挤变形 |
| 吸顶栏里的交易按钮会收起 | 往下滚时顶部不会出现两个一样的交易按钮 |
| 恢复原生滚动 | 滚动条和键盘翻页都正常了 |
| 在你同意之前不再加载统计脚本 | 你同意之前，我们不开始统计 |

判断标准很简单：**这个词能不能在产品界面上指给用户看？**指不出来就是黑话。

## 二、不说废话

废话是占了字数但没有信息量的词。删掉之后句子意思不变的，就是废话。

**没有信息量的动词**：

> 优化　提升　完善　增强　改进　升级　调整　治理

「体验优化」等于什么都没说。要么写清楚**哪里**变好了，要么整条删掉。

**营销 hype**——没有具体事实支撑的形容词：

> 全新　焕新　重磅　强势　极致　丝滑　无缝　领先　深度赋能　全面升级

**发布方视角的词**——用户不关心我们做了什么动作，只关心他现在能做什么：

| ✗ 我们的动作 | ✓ 用户的事 |
| --- | --- |
| 个股详情页上线 | 浏览器里就能看个股 |
| 选股器筛选重做 | 挑筛选条件更顺手 |
| 资讯支持 RSS 订阅 | 资讯可以用 RSS 订阅 |
| 新增交易时段说明 | 官网能查各市场的交易时段 |

「上线」「重做」「支持」「新增」是重灾区，**标题和 highlights 里一律不用**。正文里如果确实在陈述一个事实（「机构有了自己的主页」），换成用户视角的说法即可。

**但避开一种话术，不要掉进另一种。** 真实的翻车：

```
原稿  个股详情页上线网页版        ← 发布方视角，要改
改成  不用再在几个入口之间跳      ← 改成了否定式 PR 腔，一样不是人话
正解  个股页全新改版              ← 改版就说改版
```

那一版本来就是**改版**，不是新增。绕开「上线」的结果是标题读起来像加了个新东西，比原稿更误导。
**先把事实讲对，再谈措辞。** 同理，内部迁移视角也不要绕——

```
✗ 期权链从客户端搬到网页版      ← 「从哪搬到哪」是我们的事
✓ Web 支持美股期权链            ← 用户只关心网页版现在有没有
```

## 三、不写长句

一句话说一件事。**超过 30 字就断开或者删。**

不要用「，并」「，同时」「，另外」「，以及」把几件事缝成一句——那是提交记录的写法，不是给人读的。

```
✗ 财经日历五个列表改成滚多少渲染多少，长列表滚动明显更顺，日历上点日期也能切回对应列表
✓ 财经日历的长列表往下滚不卡了。点日历上的日期，下面的列表会跟着跳过去。

✗ 筛选表单的下拉整个重做，挑条件更顺手，加载时的骨架也补齐了形态，不会再跳一下
✓ 筛选条件挑起来更顺手，页面加载时也不会再跳一下。
```

也不要套娃定语。「加载时的骨架也补齐了形态」里套了三层，读到句号还没明白在说什么。

## 一版只说 3–4 件事

能写的都写上，重点就没了。这是比用词更致命的问题——用词差顶多读着别扭，
铺得太开会让读者根本找不到这版干了什么。

| 层级 | 说几件 |
| --- | --- |
| 小版本（一节） | 1–3 件 |
| 大版本总结 | 3–4 件 |

挑选标准只有一个：**读者一个月后还会记得的**。剩下的要么并进某一条里，要么不写。

真实的反例，`release-2026.07.24` 写了 5 件：

```
期权链
财务、估值页带上 AI 摘要
业绩电话会直达直播
深度页的股票筛选标签多了也能横着划，不会被挤掉      ← 这一条不该占版面
选股器可以自己定制 AI 面板                          ← 这一条也是
```

那一版真正值得说的是「Web 支持美股期权链」。后面几条颗粒度细到用户不会专门记住，
把它们摆上去，等于让读者自己从五件事里猜哪件重要。

判断一条该不该留，问：**这条如果删掉，这一版还完整吗？** 答案是「完整」，就删掉。

## 标题怎么写

标题是列表页上唯一的扫读依据，版本号和日期站点会自己补，所以标题要回答**用户的一个问题**：

- 我现在能做什么了？
- 什么事变容易了？
- 哪个烦人的问题没了？

一句话，中文不超过 16 字，英文不超过 60 字符，不带句号。

```
✓ 浏览器里就能看个股
✓ 长图不再被裁掉一半
✓ 划一段话就能问 AI
✓ 修好交易密码下打不开账户设置的问题     ← 纯修复版本就写修了什么

✗ Longbridge Web 2026.09.21              ← 脚本占位
✗ 选股器重做，发帖能带我的持仓            ← 「重做」是我们的动作
✗ 资讯图片按原始比例显示                  ← 陈述现象，没说好在哪
✗ 体验优化与问题修复                      ← 废话
```

一版动了好几块，挑最值得说的一到两件，剩下的交给 `summary`。

## 有事实才能写数字

不许编造性能数字、用户量、准确率、节省的时间。有实测就写实测，没有就用「更快」这类模糊说法，**不要自己折算一个倍数**。

```
有证据：首屏从 850ms 降到 210ms    → 可以写「打开快了大约 4 倍」
没证据                            → 只能写「打开更快」
```

同理，「更快」本身也要有依据——看到一条 perf 提交不等于用户能感知。拿不准就不写。

## 交稿前自查

- [ ] 这一版说了几件事？小版本超过 3 件、大版本超过 4 件就砍
- [ ] 事实本身对不对——是新增还是改版？受众是哪个站点？
- [ ] 通读一遍，有没有指不出来的词（黑话）
- [ ] 每句话删掉形容词后意思变了吗？没变说明那是废话
- [ ] 有没有超过 30 字的句子
- [ ] 标题回答了「用户现在能做什么」吗
- [ ] 每个数字都能指向一条证据吗
